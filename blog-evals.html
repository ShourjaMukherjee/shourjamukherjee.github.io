What goes into a basic eval

An eval is an exam for a model, and it has three pieces: a dataset of questions with known answers, the model you are testing, and a grader that decides whether each answer is right. If you ask a model for five capital cities and it gets four right and says Sydney for Australia, the score is 80%, and that is already a complete eval.

Most of the decisions are in the grader. Exact match works when there is one right answer, although it will mark "Paris, France" wrong against "Paris" unless you normalise first. A code check, like running the tests or validating the JSON, is great when the output is structured. Humans can grade open-ended answers and are slow and expensive. Using another model as a judge scales well, and the judge makes its own mistakes, so you need to spot-check it. I use the simplest grader that works for the task.

There are a few rules I try to hold to. Keep eval questions out of the training data, since a model that has seen the exam tells you nothing. Keep the question set fixed, otherwise two scores aren't comparable. Read the wrong answers as well as the number. Break the score down by category, because 80% overall can hide 99% on easy questions and 20% on hard ones. And record which model, dataset and grader versions produced a number, so that someone else can reproduce it.

The other thing worth knowing is how noisy small evals are. On 100 questions, a score of 80% has a 95% interval of roughly ±8 points, so 80 and 83 could easily be the same model. On 1,000 questions it is about ±2.5. It gets worse when questions share a passage, which I wrote about in this note.
