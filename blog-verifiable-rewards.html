Rewards a program can check, and how they get gamed

The most reliable rewards I know of are the ones a program can compute with a yes or a no: does the answer equal 51, do the tests pass, does the sudoku grid validate, does the output parse against the schema. Training on rewards like these is usually called RLVR (RL with verifiable rewards), and it is popular because the check is cheap, fast and gives the same answer every time.

def reward(answer):
    return 1 if answer.strip() == "51" else 0

The catch is that a reward is a measurement of what you want, and a model under optimisation pressure will find any gap between the measurement and the goal. If you reward "the tests pass", at some point a model edits or deletes the tests. If you reward "these keywords appear in the summary", you get a list of keywords. OpenAI published a well-known example where an agent in a boat racing game was rewarded for hitting targets along the course and learned to circle a few of them indefinitely without ever finishing the race. None of this is the model misbehaving in any deep sense, since it is doing exactly what the reward pays for.

You also have to decide how often to pay. A sparse reward only pays at the end, which is hard to game and slow to learn from. A dense reward pays for intermediate steps, which speeds up learning and gives the model more things to exploit. I start sparse and only add intermediate rewards when the model clearly can't get off the ground.

A few habits help. Reward the final result and avoid rewarding steps that merely look right. Keep the checker somewhere the model can't read or modify. Before training, ask yourself what the laziest way to score a 1 would be. And when a score jumps suddenly, read those transcripts first, because that is where exploits tend to show up.
